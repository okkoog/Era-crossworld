# ERA CrossWorld 분산형 연동 구조 기획서 v0.2

> 상태: 초기 아키텍처 제안 / 미검증
>
> 목적: 여러 ERA 게임을 하나의 거대한 프로젝트로 통합하는 대신, 각 게임을 독립 실행 상태로 유지하면서 공용 데이터와 C# 코어를 통해 하나의 세계처럼 연결하는 구조를 정리한다.
>
> 채택 조건: 아래의 "최초 기술 검증"이 실제 런타임에서 PASS될 경우 정식 개발 후보로 승격한다.

---

## 1. 기본 개념

ERA CrossWorld는 여러 ERA 게임의 소스와 콘텐츠를 하나의 거대한 게임 안에 합치는 것을 기본 목표로 하지 않는다.

각 게임은 가능한 한 **독립된 ERA 게임으로 유지**한다.

CrossWorld는 이 게임들을 연결하여 플레이어가 하나의 세계를 이동하는 것처럼 느낄 수 있도록 하는 **공통 데이터 및 게임 이동 시스템**을 담당한다.

즉,

> **게임을 하나로 합치는 것이 아니라, 게임 사이에서 캐릭터와 세계의 상태가 이동하도록 만든다.**

---

## 2. 기본 구조

전체 구조는 다음 네 부분으로 구성한다.

```text
                 CrossWorld Core
                       │
          ┌────────────┼────────────┐
          │            │            │
       게임 A        게임 B        게임 C
      ERA 게임       ERA 게임       ERA 게임
          │            │            │
       Adapter A     Adapter B     Adapter C
```

각 게임은 서로의 소스를 직접 알 필요가 없다.

게임 A는 게임 B의 변수를 읽지 않는다.

게임 A가 알아야 하는 것은 오직 다음뿐이다.

```text
게임 A 데이터
      ↕
CrossWorld 공통 데이터
```

게임 B 역시 동일하다.

---

## 3. 구성 요소

### 3.1 ERA 게임

각 콘텐츠의 실제 플레이를 담당한다.

예:

- 유희왕 ERA
- 야구 ERA
- 전략 ERA
- RPG ERA
- 경마 ERA
- 포켓몬 ERA
- 아이돌/버튜버 ERA

각 게임은 기존 게임을 기반으로 개조할 수도 있고, CrossWorld 전용으로 새로 만들 수도 있다.

가능한 한 게임 자체의 구조는 독립적으로 유지한다.

### 3.2 CrossWorld Adapter

각 게임과 CrossWorld 사이의 번역기다.

예를 들어 게임 A에서

```text
BASE:0 = 체력
MONEY = 소지금
TALENT:30 = 검술재능
```

이라고 사용하고,

게임 B에서는

```text
PLAYER_HP
GOLD
SKILL_SWORD
```

라고 사용하더라도 CrossWorld에서는 이를

```text
character.hp
character.money
character.skill.sword
```

같은 공통 데이터로 변환한다.

게임마다 Adapter 하나를 둔다.

```text
게임 A ↔ Adapter A ↔ CrossWorld
게임 B ↔ Adapter B ↔ CrossWorld
게임 C ↔ Adapter C ↔ CrossWorld
```

따라서 게임이 10개가 되어도 게임끼리 서로 직접 호환할 필요가 없다.

## 4. C# CrossWorld Core

현재 저장소에서 이미 검증된

```text
ERB
 ↓ CALLSHARP
C# Plugin
```

구조를 적극적으로 사용한다.

현재 런타임 테스트에서는 다음이 이미 확인되었다.

- ERB → C# 호출
- C# → ERB 값 반환
- 정수/문자열 참조 전달
- GLOBAL 직접 접근
- DataTable 직접 접근
- C# 내부 계산 처리

따라서 장기적으로는 C#을 단순 보조 계산용이 아니라 **CrossWorld의 핵심 관리 계층**으로 사용한다.

현재 저장소의

```text
core/CrossWorld.Core/
```

를 이 역할로 사용한다.

---

## 5. CrossWorld Core의 역할

CrossWorld Core는 다음을 담당한다.

```text
공용 세이브 읽기/쓰기
캐릭터 고유 ID 관리
게임별 Adapter 호출
게임 이동 요청 처리
게임별 데이터 보존
공통 데이터 변환
버전 관리
세이브 무결성 검사
게임 실행 요청
게임 간 전달 데이터 관리
```

반대로 실제 게임 플레이는 담당하지 않는다.

예를 들어 야구 경기 계산은 야구 ERA가 한다.

CrossWorld Core는

```text
이 캐릭터가 야구 선수다.
현재 야구 경력은 이것이다.
다른 게임에서도 사용할 공통 명성은 이것이다.
```

정도만 관리한다.

## 6. 데이터 구조

CrossWorld 데이터는 크게 세 종류로 나눈다.

### 6.1 공통 데이터

여러 게임에서 의미가 있는 데이터.

예:

```text
Character ID
이름
성별
나이
공통 신체정보
현재 소지금
명성
인간관계
소속
공통 아이템
세계 공통 플래그
```

공통 데이터는 최소화한다.

### 6.2 게임 전용 데이터

특정 게임에서만 의미가 있는 데이터.

예:

```text
YuGiOh:
    카드 목록
    덱
    듀얼 전적
    카드 숙련도

Baseball:
    타율
    홈런
    포지션
    구속
    변화구

HorseRace:
    혈통
    레이스 기록
    거리 적성

Idol:
    팬 수
    방송 숙련도
    가창력
```

다른 게임은 이 데이터를 해석할 필요가 없다.

다만 CrossWorld 저장소에는 계속 보존한다.

### 6.3 게임 내부 데이터

CrossWorld에 전달할 필요조차 없는 데이터.

예:

```text
이벤트 진행용 임시 변수
UI 상태
현재 메뉴 위치
전투 임시 변수
랜덤 이벤트 내부 카운터
```

이런 데이터는 기존 게임 세이브에만 저장한다.

## 7. 공용 세이브 개념

예시:

```text
CrossWorldSave/
│
├─ world.json
│
├─ characters/
│   ├─ CW000001.json
│   ├─ CW000002.json
│   └─ CW000003.json
│
└─ games/
    ├─ yugioh/
    ├─ baseball/
    ├─ megaten/
    └─ idol/
```

캐릭터 하나를 예로 들면:

```text
CW000001

    이름 = 크로
    돈 = 125000
    명성 = 32

유희왕:
    듀얼랭크 = 18
    덱 = ...
    전적 = ...

야구:
    포지션 = 투수
    구속 = 151
    통산승 = 38

RPG:
    레벨 = 42
    직업 = 검사
```

현재 실행 중인 게임은 자기 데이터만 불러온다.

## 8. 게임 간 이동

게임 A에서 특정 장소나 기능을 이용하면 다른 게임으로 이동할 수 있다.

예:

```text
[중앙역]

어디로 이동하시겠습니까?

[1] 듀얼 시티
[2] 프로야구 지구
[3] 모험자 지구
[4] 경마 지구
```

플레이어가 프로야구 지구를 선택하면:

```text
게임 A
 ↓
현재 상태 CrossWorld에 저장
 ↓
게임 B 이동 요청
 ↓
게임 A 종료
 ↓
CrossWorld Launcher
 ↓
게임 B 실행
 ↓
게임 B Adapter
 ↓
CrossWorld 데이터 로드
 ↓
플레이 재개
```

사용자 입장에서는 이것을 **지역 이동**처럼 보이게 만든다.

## 9. CrossWorld Launcher

게임 전환을 담당하는 별도 프로그램을 둔다.

가칭:

```text
CrossWorldLauncher.exe
```

주요 역할:

```text
현재 실행 게임 확인
이동 대상 확인
현재 게임 종료 확인
다음 게임 실행
세이브 슬롯 전달
캐릭터 ID 전달
오류 발생 시 복구
```

Launcher는 처음부터 거대한 프로그램일 필요가 없다.

초기에는 단순히

```text
transfer.json
```

같은 파일을 확인하고 대상 EXE를 실행하는 정도면 충분하다.

## 10. 이동 정보

게임 전환 직전에 다음과 같은 정보를 남긴다.

```text
FROM_GAME = RPG
TO_GAME = BASEBALL

CHARACTER_ID = CW000001

ENTRY_POINT = TOKYO_STATION

TRANSFER_TYPE = NORMAL
```

게임 B는 시작하면서 이것을 읽는다.

그러면

```text
당신은 도쿄역에 도착했다.
```

같은 형태로 자연스럽게 진입시킬 수 있다.

---

## 11. 시간 처리

초기에는 모든 게임의 시간을 완전히 동기화하지 않는다.

세계 시간까지 즉시 완전 통합하면 시스템 복잡도가 지나치게 커진다.

초기 권장 구조:

```text
CrossWorld 공통 날짜
+
각 게임 내부 진행 시간
```

예를 들어 야구에서 하루가 지나면 반드시 RPG 내부 이벤트가 하루씩 진행될 필요는 없다.

필요한 경우에만 CrossWorld 공통 날짜에 영향을 준다.

완전한 시간 동기화는 후속 단계에서 검토한다.

---

## 12. NPC 처리

캐릭터마다 CrossWorld 고유 ID를 부여한다.

예:

```text
CW_CHAR_000001 = 플레이어
CW_CHAR_000002 = 캐릭터 A
CW_CHAR_000003 = 캐릭터 B
```

각 게임은 자기 내부 캐릭터 번호와 매핑한다.

```text
게임 A의 CHAR:37
        ↓
CW_CHAR_000002
        ↓
게임 B의 CHAR:152
```

이를 통해 서로 다른 게임에서도 같은 인물임을 인식할 수 있다.

---

## 13. 캐릭터 능력치 호환

모든 능력치를 그대로 공유하지 않는다.

예를 들어:

```text
게임 A 체력 = 700 / 1000
```

이라면 CrossWorld에는

```text
physical.stamina = 0.7
```

처럼 정규화된 값을 둘 수 있다.

게임 B에서는 이를

```text
게임 B 체력 = 70 / 100
```

으로 변환한다.

그러나 야구의 구속이나 유희왕의 카드 숙련도 같은 것은 굳이 변환하지 않는다.

---

## 14. 게임 독립성

이 구조에서 가장 중요한 원칙 중 하나다.

게임 A가 없어도 게임 B는 실행되어야 한다.

게임 C에 오류가 생겨도 게임 A와 B는 영향을 받지 않아야 한다.

CrossWorld 전체가 다음 구조를 갖는다.

```text
CrossWorld Core

게임 A 1.2
게임 B 0.8
게임 C 3.1
게임 D 1.0
```

각 게임은 독립적으로 업데이트할 수 있다.

---

## 15. 리소스 관리

통합형 구조:

```text
CrossWorld 실행

→ 모든 게임 ERB
→ 모든 CSV
→ 모든 캐릭터
→ 모든 시스템
→ 모든 리소스
```

분산형 구조:

```text
야구 플레이

→ 야구 ERA
→ 야구 데이터
→ 공통 CrossWorld 데이터
```

따라서 게임 수가 늘어나더라도 현재 플레이하지 않는 게임의 대량 리소스를 실행 중에 유지할 필요가 없다.

이는 대규모 CrossWorld에서 상당한 장점이 될 수 있다.

---

## 16. 기존 ERA 게임 활용

CrossWorld 전용 게임을 처음부터 전부 새로 만들 필요는 없다.

기존 ERA 게임에 Adapter를 추가하여 CrossWorld 대응 게임으로 개조하는 방식도 사용한다.

예:

```text
기존 eraMegaten
       ↓
CrossWorld Adapter 추가
       ↓
CrossWorld 대응 RPG
```

원본 시스템은 최대한 유지한다.

필요한 부분만 수정한다.

---

## 17. AI 역공학 활용

기존 ERA 게임의 구조가 복잡한 경우 AI를 이용해 다음을 분석한다.

```text
주요 변수
캐릭터 구조
저장 구조
시스템 진입점
주요 함수
데이터 의존관계
```

그 후 CrossWorld Adapter에서 필요한 부분만 연결한다.

목표는 게임 전체를 다시 만드는 것이 아니다.

> **CrossWorld와 연결하는 데 필요한 인터페이스를 찾는 것**이다.

## 18. 기술적으로 현재 확인된 것

현재 CrossWorld 저장소 기준으로 실제 런타임에서 검증된 기반:

```text
Emuera.NET 실행

ERB
 ↕
CALLSHARP
 ↕
C# Plugin

GLOBAL 접근
DataTable 접근
값 전달

```

따라서 C# CrossWorld Core를 사용하는 방향은 현재 엔진 구조와 맞는다.

관련 기준 자료:

- `test/ERA_CrossWorld_Runtime_Test_0.4.3/docs/RUNTIME_TEST_0.4.3_README.txt`
- `test/ERA_CrossWorld_Runtime_Test_0.4.3/plugin_src/CrossWorld.RuntimeTest.Plugin/Plugin.cs`

## 19. 아직 검증되지 않은 것

다음은 별도 런타임 테스트가 필요하다.

```text
C# → 외부 파일 생성
C# → 외부 파일 읽기

C# → 다른 EXE 실행

ERA A 종료
↓
Launcher
↓
ERA B 실행

게임 A → CrossWorld Save → 게임 B

게임 B → CrossWorld Save → 게임 A
```

이 단계가 성공하면 분산형 CrossWorld의 핵심 기술은 사실상 성립한다.

## 20. 최초 프로토타입

처음부터 실제 게임을 두 개 연결하지 않는다.

아주 작은 테스트 게임 두 개를 만든다.

### Game A

화면:

```text
현재 게임: A
캐릭터 이름: 크로
돈: 1000

[1] 돈 +100
[2] 게임 B로 이동
```

### Game B

```text
현재 게임: B
캐릭터 이름: 크로
돈: 1100

[1] 돈 +500
[2] 게임 A로 이동
```

목표:

```text
A 실행
↓
돈 100 증가
↓
B 이동
↓
B에서 1100 확인
↓
돈 500 증가
↓
A 복귀
↓
A에서 1600 확인
```

이것만 성공하면 된다.

## 21. 개발 단계

### 단계 1 — CrossWorld Transfer Test

목표:

```text
ERA A
↔
ERA B
```

간단한 데이터 하나를 공유하고 자동으로 게임을 전환한다.

### 단계 2 — Character ID

캐릭터 고유 ID를 만든다.

```text
CW000001
```

게임별 CHAR 번호와 연결한다.

### 단계 3 — 공용 세이브

공통 데이터와 게임 전용 데이터를 분리한다.

### 단계 4 — Adapter 규격

게임이 CrossWorld에 대응하기 위한 최소 규칙을 정의한다.

예:

```text
CrossWorld_Load()
CrossWorld_Save()
CrossWorld_Enter()
CrossWorld_Leave()
```

### 단계 5 — 실제 ERA 게임 1개 연결

기존 ERA 게임 하나를 골라 CrossWorld Adapter를 만든다.

### 단계 6 — 실제 ERA 게임 2개 연결

서로 완전히 다른 장르의 ERA 두 개를 연결한다.

이 단계에서 실제로 구조가 확장 가능한지 판단한다.

### 단계 7 — CrossWorld Hub

역, 포털, 세계 지도 등 게임 간 이동을 실제 게임 시스템으로 만든다.

```text
   유희왕      야구    RPG     전략       경마
     │          │       │       │          │
     └──────────┴───────┼───────┴──────────┘
                        │
                 공통 캐릭터 세계
```

플레이어는 이것을 여러 게임이라고 생각하지 않는다.

세계 안에서

```text
오늘은 카드 대회 참가
↓
기차를 타고 이동
↓
다음 지역에서 야구 경기
↓
며칠 후 RPG 의뢰 수행
```

처럼 활동하는 하나의 세계로 경험한다.

내부적으로만 여러 ERA 실행 파일이 존재한다.

---

## 23. 이 방식의 핵심 장점

1. 모든 ERA 소스를 하나로 합치지 않아도 된다.
2. 현재 플레이하는 게임의 리소스만 로드할 수 있다.
3. 기존 ERA 작품의 시스템을 활용하기 쉽다.
4. 한 게임의 오류가 전체 프로젝트를 망가뜨릴 가능성이 줄어든다.
5. 게임별 개발과 업데이트가 독립적이다.
6. 게임마다 완전히 다른 데이터 구조를 허용할 수 있다.
7. 새로운 게임을 CrossWorld에 추가하기 쉬워진다.
8. C#을 공통 코어로 활용할 수 있다.
9. AI를 이용한 기존 ERA 분석 및 Adapter 제작과 궁합이 좋다.
10. 처음에는 아주 작은 프로토타입으로 기술 가능성을 검증할 수 있다.

---

## 24. 현재 권장 방향

기존의

> **9개 콘텐츠를 하나의 거대한 ERA 게임 안에 구현한다**

방식은 폐기하지 않는다.

하지만 기본 아키텍처 후보를 다음과 같이 변경한다.

> **각 콘텐츠를 독립 실행 가능한 게임 모듈로 만들고, CrossWorld Core와 공용 세이브를 이용하여 하나의 세계처럼 연결한다.**

콘텐츠에 따라 작은 시스템은 기존 게임 안에 직접 포함할 수 있다.

즉 완전 분산형을 강제하지 않고,

> **큰 콘텐츠는 독립 게임 / 작은 콘텐츠는 내부 모듈**

형태의 혼합 구조도 허용한다.

---

## 25. 최초 기술 검증

현재 시점에서 가장 먼저 검증할 것은 게임 콘텐츠가 아니다.

다음 하나다.

> **ERA 게임 A에서 C#을 호출하여 데이터를 저장하고, 게임 A를 종료한 뒤 게임 B를 자동 실행하여 같은 데이터를 불러올 수 있는가?**

이 실험이 PASS하면 분산형 CrossWorld 설계를 정식 개발 후보로 채택한다.

FAIL하면 실패 원인을 확인한 뒤 Launcher 구조 또는 다른 프로세스 전환 방식을 검토한다.

이 테스트 이전에는 대규모 분산형 구현에 착수하지 않는다.


---

## 26. 초기 연동 대상 우선순위 변경

분산형 연동 구조를 채택함에 따라 초기 콘텐츠 선정 기준을 변경한다.

기존에는 CrossWorld에 넣고 싶은 장르를 먼저 정하고 필요한 시스템을 새로 구현하는 방향을 폭넓게 검토했으나, 분산형 구조에서는 **이미 ERA 게임으로 존재하는 작품을 우선 연결하는 방식**이 개발 비용과 검증 난이도 측면에서 유리하다.

따라서 초기 연동 대상은 다음을 우선 검토한다.

### 26.1 우선 연동 후보

1. **eraOCG**
   - 유희왕 / 카드게임 콘텐츠 담당
   - 카드 수집, 덱 구축, 듀얼, 대회 등의 기존 시스템 활용을 우선 검토한다.

2. **era말딸**
   - 육성 / 경주 / 커리어 콘텐츠 담당
   - 기존 육성 및 레이스 구조를 CrossWorld에 연결하는 방식을 우선 검토한다.

3. **era메가텐**
   - RPG / 전투 / 탐험 / 악마 관련 콘텐츠 담당
   - 던전, 전투, 파티, 악마 등의 기존 시스템 활용을 우선 검토한다.

4. **eraTW**
   - 단순한 추가 콘텐츠로 넣을지는 미정이다.
   - 일상물 성격이 강하므로 별도 콘텐츠 하나로 추가하는 가치가 낮을 수 있다.
   - 대신 장소 이동, 일상 루프, 캐릭터 상호작용 등 기존 구조를 분석하여 **CrossWorld Base / Hub의 기반으로 전환할 수 있는지** 검토한다.

### 26.2 eraTW의 별도 검토 방향

eraTW는 다음 두 가지 후보 중 하나로 본다.

#### A. 독립 연동 게임

다른 ERA와 동일하게 별도 실행 게임으로 유지한다.

```text
CrossWorld Base
 ├─ eraOCG
 ├─ era말딸
 ├─ era메가텐
 └─ eraTW
```

#### B. CrossWorld Base로 전환

eraTW의 일상생활·장소·캐릭터 상호작용 구조가 재사용하기 적합하다면, 이를 CrossWorld의 기본 생활 세계와 허브로 개조하는 방안을 검토한다.

```text
        eraTW 기반 CrossWorld Base
                    │
        ┌───────────┼───────────┐
        │           │           │
     eraOCG      era말딸      era메가텐
```

이 경우 eraTW는 네 번째 콘텐츠라기보다 다음 기능을 담당하는 **CrossWorld 본체 후보**가 된다.

- 집 및 생활 거점
- 거리와 시설
- 캐릭터와의 일상 상호작용
- 공통 시간 진행
- 공통 이벤트
- 다른 ERA 게임으로 이동하는 허브

실제 채택 여부는 eraTW의 소스 구조를 분석한 뒤 판단한다.

특히 다음을 우선 확인한다.

1. 장소 이동 구조를 CrossWorld용으로 확장하기 쉬운가.
2. 캐릭터 데이터 구조를 공용 Character ID와 연결하기 쉬운가.
3. 기존 일상 루프를 필요한 만큼 제거·수정·확장할 수 있는가.
4. CrossWorld Adapter와 C# Core를 연결해도 기존 구조와 충돌이 크지 않은가.

### 26.3 신규 구현 콘텐츠의 우선순위

기존 설계 초안의 야구, 축구, 전략, 포켓몬, 아이돌/버튜버 등은 폐기하지 않는다.

다만 초기 단계에서는 다음 순서를 적용한다.

```text
1순위: 이미 ERA 게임이 존재하는 콘텐츠의 연동
2순위: CrossWorld Base / Hub 확립
3순위: 기존 ERA를 활용하기 어려운 콘텐츠의 신규 구현
```

따라서 초기 실개발 범위는 우선 다음과 같이 축소한다.

```text
[CrossWorld Base 후보]
- eraTW 기반 전환 검토

[초기 연동 게임]
- eraOCG
- era말딸
- era메가텐

[후순위]
- ERA 게임이 존재하지 않는 장르
- 대규모 신규 시스템 구현이 필요한 콘텐츠
```

이 변경의 목적은 기존 9개 콘텐츠 구상을 폐기하는 것이 아니라, **분산형 구조의 장점을 살려 이미 완성된 ERA 게임을 먼저 연결하고 CrossWorld의 핵심 연동 구조를 조기에 검증하는 것**이다.
