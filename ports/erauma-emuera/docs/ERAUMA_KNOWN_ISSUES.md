# 원본과의 차이와 검증 제한

기록일: 2026-10-01, 포트 0.3.2. 이번 호환판은 보존된 EraUma v3.113 (ryuki) JavaScript를 Emuera.NET에서 단독으로 실행한다. 게임 규칙을 바꾸거나 원본을 ERB로 다시 작성하지 않았다. **0.3.0 직접 시험 실패와 0.3.1 레이스 화면 깜빡임이 확인됐으며 0.3.2 수정 후 전체 직접 플레이는 아직 미확인**이다. 아래 차이와 검증 범위를 유지보수 시 함께 확인한다.

## 0.3.1 레이스 깜빡임과 0.3.2 수정의 자동 검증

사용자는 0.3.1이 이전보다 부드러워졌다고 보고했지만 레이스 화면은 계속 깜빡였다. 60fps·310프레임·5.1667초 영상에서 canvas 전체가 비는 구간 45회·114프레임(36.8%)을 확인했고 각 구간은 약 17–67ms였다. 이전 그림이 계속 남는 중첩 현상이 아니라 완성 화면 사이에 빈 화면이 노출되는 결함이다.

실행기는 이미 double buffering을 사용한다. `api.ClearDisplay` (`EmueraConsole.ClearDisplay`)가 모든 행과 여백을 다시 출력하기 전에 강제 paint를 수행한 것이 원인이다. 0.3.2의 `NativeFrameUpdate`는 엔진의 `console.SetRedraw(0)` 플래그와 managed `PictureBox.Paint` 처리로 교체 중 이전 완성 bitmap을 유지한다. 마지막에 handler와 엔진 갱신 상태를 복원하고 완성 프레임을 강제 출력한다. 일반 버튼·스크롤 처리는 갱신 범위 밖의 native 경로로 유지한다.

`Test-FramePaint.ps1`은 정확한 배포 실행기의 Paint callback과 native/수정된 `PictureBox.OnPaint` delegate 연결을 시험 bitmap에 기록한다. 0.3.1 대조는 7회 전환의 중간 그림 165회로 예상 FAIL(`outputs/frame-paint-6b0c25c1/summary.json`), 수정판은 전체·부분·추가 출력·표시 지연을 포함한 같은 7회 전환의 중간 그림 0회로 PASS(`outputs/frame-paint-6134aec5/summary.json`)다. 모든 최종 그림 변경·타이머 진행·handler 수 2→2·이후 새로고침 3회의 복원을 확인했다. PNG 기록이 callback을 늦추므로 165회는 실제 화면 fps가 아니다. 데스크톱 캡처·OS 입력·사람의 직접 플레이 결과와 구별한다.

원본 레이스 연속 20회 갱신도 중간 그림 0회·모든 최종 그림 변경·native Paint 40회·handler 2→2·이후 새로고침 3회 복원으로 PASS했다(`outputs/frame-paint-9860cf1a/summary.json`). 이 경로는 격리한 fixture 시험에서 500ms 가상 시간 전진을 사용한다. 별도 실행기의 실제 경과 시간 타이머도 PASS다.

0.3.2는 호스트 기본 10개·API 21개·저장 10개·플레이 46개·UI 21개, 입력 출력 4프레임의 미관리 행 0, 입력 루프 7단계와 타이머 tick 1회, 원본 canvas 23개(전체 26회·부분 27회·205행 보존·경고 0), 실행기 7단계를 통과했다. 근거는 `evidence/0.3.2/README.md`에 있다. 같은 배포 구성의 공백 경로 이동 검사에서 원본 화면 23개와 레이스 연속 갱신 20회가 PASS했다. ZIP의 개별 파일 해시는 `package-manifest.json`과 생성 검증 보고서로 확인한다. 전체 직접 레이스·저장·완전 종료·재실행·로드·후속 행동과 실제 음악 청취가 남아 있으며 자동 검사만으로 사람의 깜빡임 해결 확인을 기록하지 않는다.

## 0.3.0 직접 시험 실패와 0.3.1 수정의 역사적 근거

사용자는 빈 화면 클릭으로 대사가 진행되지 않고 Enter만 반응하며, 선택할 때 이전 그림·메뉴가 겹쳐 남는 문제를 보고했다. 모집 화면의 반복 중첩을 확인한 뒤 레이스 전에 직접 시험을 중단했다. 이를 미확인으로만 기록하거나 이전 자동 PASS로 대체하지 않고 **0.3.0 직접 시험 실패**로 기록한다.

대사 대기도 `INPUTS`로 처리해 빈 클릭이 입력되지 않는 것이 첫 원인이다. 0.3.1은 선택지·현재 URL·입력 규칙이 없는 `any` 대기를 `WAIT`/`TWAIT`로 분리한다. 번호 선택·자유 문자열·`any`와 규칙을 함께 지정한 입력·현재 URL은 `INPUTS`/`TINPUTS`를 유지한다. 읽기 전용 `input-kind` 조회로 두 경로를 고른다.

두 번째 원인은 `INPUTS`가 입력값을 native 논리 줄로 출력하는데 부분 갱신이 그 줄을 계산하지 않은 것이다. 이전 그림·버튼의 일부 행이 입력마다 남았다. 0.3.1은 화면 갱신 전에 추가 입력 출력 줄을 제거한다. 원본 모집 화면의 실제 입력 재현에서 입력 출력은 수정 전후 모두 `[1,1,1]`줄이며, 미관리 줄은 수정 전 `[0,1,2,3]`에서 수정 후 `[0,0,0,0]`으로 바뀌어 회귀 검사를 통과했다.

21개 호스트 UI 회귀와 `Game.ERB` 입력 루프의 관리형 엔진 검사는 PASS했다. 빈 클릭이 막히는 이전 `INPUTS` 대조, `WAIT` 빈 클릭, `TWAIT` 시간 초과 뒤 빈 클릭, 실제 번호 7·`any` 선택 8·타이머 선택 9·문자열 `Trainer`과 URL의 값 입력 유지를 확인했다. 격리한 시험 프로세스 내부의 입력 처리 검사이며 OS 입력이나 사람의 직접 클릭은 아니다. 수정 후 전체 직접 경로와 실제 음향 청취도 미확인이다. 아래 0.3.0 renderer·화면 보고서는 실제 입력 출력을 우회한 자동 근거이며, 이번 사용자 실패를 발견하지 못했다.

## 확인한 입력과 오류 처리

2026-09-30 사용자가 실제 Emuera에서 `5` → `Trainer` → `Finish`를 입력해 PASS를 확인했다. 결과 파일에도 숫자·문자열·버튼 연결의 정상 완료가 기록됐다. 이는 0.2 입력 시험이며 새 UI의 직접 플레이 결과로 확대하지 않는다. 당시 Windows 화면 캡처가 시간 초과되어 사용자 확인과 결과 파일을 근거로 했다.

0.3에서 실제 Emuera의 renderer를 실행한 자동 probe는 24열·색상·정렬·진행 막대·crop·레이어·전체 계열 그래프와 native 버튼 ID를 확인했다. 진행 막대는 65%·0%·100%·높이 6px·offset의 5개 픽셀 검사를 통과했다. 새 게임·원본 타이틀·메인·트레이닝·정보·아이템·외출·상점·레이스 진행/재생·결과·저장을 포함한 23개 canvas 경로를 자원 있음/없음 양쪽에서 검사했다. 자원 있음 `runtime-UiScreens-fce0e490`은 전체 갱신 27회·부분 갱신 27회·205행 보존, 자원 없음 `runtime-UiScreens-9717a264`는 전체 갱신 26회·부분 갱신 27회·205행 보존이다. 공식 리소스 URL `https://umaera.gitgud.site/data/uma-resource/full.html`의 shell 브라우저 실행도 자동 검사에서 통과했다. 이 확인은 Windows 데스크톱 캡처나 사람이 메뉴·URL 버튼을 직접 클릭한 기록이 아니다. 비활성 버튼 5는 클릭 대상이 아니며 `isButton:false`인 선택지 6의 native 클릭 ID는 유지한다.

0.3.0 native 음향 보고서 `outputs/native-ui-audio-0027b902/native-ui-summary.json`은 Windows Media Player의 재생·일시정지·재개·반복·Dispose와 실행 중 음량 변경을 통과했다. 음량 변경 뒤 같은 Sound 인스턴스·재생 위치의 진행·일시정지·반복 상태가 유지되고 재생을 다시 시작하지 않으며 오류·경고는 0개다. 음량 0 시험이므로 실제 청취는 미확인이다.

부분 `clear`, 마지막 행 `replace`, 논리 행 수, 이전 버튼 비활성화, 정규식·번호 검사, 대기 입력 교체, 타이머 선택지와 취소를 호환 계층에서 처리한다. 원본에서 보고 후 계속 진행하는 저장 실패·없는 kojo 키는 진단으로 남긴다. 알 수 없는 모듈이나 렌더링 형태, 미처리 JS 오류는 실행 오류로 드러난다.

## 저장과 플레이 검증 범위

0.3.0 코드 동결 후 호스트 기본 10개·API 21개·저장 10개·플레이 46개·UI 16개와 같은 플러그인 DLL의 실제 Emuera 7단계 최종 회귀는 PASS다. 훈련·레이스 시나리오 20개와 별도 프로세스 복원 5개도 통과했다. 이 자동 결과를 전체 직접 플레이로 확대하지 않는다.

원본 API의 JSON/gzip 저장과 새 JS 엔진에서의 복원, 실제 Emuera 프로세스 종료·재실행 뒤 전체 게임 데이터 일치를 검증했다. 원본 Electron으로 만든 사용자 저장을 가져오기와 반대 방향 로드는 검증하지 않았다. 형식과 저장 구현을 재사용했다는 사실만으로 모든 기존 저장과의 상호 운용을 보증하지 않는다.

선택한 새 게임·캐릭터·행동·이벤트 분기를 검증한다. 모든 캐릭터 대사, 난수 이벤트, 장기 엔딩, 모든 언어·설정 조합을 전수 실행한 것은 아니다. 구체적인 완료 경로와 증거는 [이식 현황](ERAUMA_PORTING_STATUS.md)에 기록한다. 원본 Electron과 같은 초기 데이터·난수 조건에서 계산 결과를 비교하는 시험도 아직 수행하지 않았다.

재현용 플레이 시나리오는 시험 안에서 난수를 고정한다. 일반 게임 실행의 `Math.random`은 바꾸지 않는다. 고정 난수로 반복한 호환판 시험은 원본 Electron과의 계산 결과 비교를 대신하지 않는다.

늦게 추가되는 선택지는 호스트의 가상 시간 시험과 실행기의 실제 경과 시간 `AWAIT`/`tick` 시험으로 검사한다. 일반 게임의 타이머 입력은 보이는 창에서 `TINPUTS`를 사용하지만, 해당 입력 대기의 직접 조작은 별도로 확인하지 않았다. 숨겨진 창에서 무인 시험을 실행할 때 `TINPUTS` 내부 타이머가 시작되지 않을 수 있어 시험은 `AWAIT`로 진행한다.

## 버전과 성능

업로드 ZIP에 원본 engine gitlink가 없어 조사한 엔진 API 커밋을 고정했다. 의존성을 업데이트할 때는 원본 게임의 시작·입력·저장·레이스를 다시 검증해야 한다. CommonJS와 Node 호환 기능은 이 게임이 사용하는 범위로 한정한다.

게임 프로파일은 호출당 최대 2GB의 JS 할당, 2천만 문장, 180초 제한을 사용한다. 입력·타이머 대기는 ERB로 반환하지만 JS 계산은 같은 스레드에서 처리하므로 큰 계산 중 화면 반응이 늦어질 수 있다. 32비트 Windows, 저메모리 PC, 장기 플레이의 메모리 증가와 다수 캐릭터 처리 부하는 검증하지 않았다. 성능 관찰치는 시험 조건과 함께 상태 문서에 기록한다.

## 배포와 범위

개발용 `Build.ps1` 출력은 로컬 절대 경로를 참조한다. 배포용 `Package.ps1` 출력은 원본 소스·생성 kojo·설치된 공식 `game/res/`를 포함하고 상대 경로를 사용한다. 자원 저작물은 Git에 추가하지 않는다. Node는 kojo를 빌드할 때만 필요하다. kojo-loader 컴파일러 자체는 명시적 라이선스를 확인하지 못해 재배포하지 않는다. 설치·재다운로드 절차는 [포트 README](../README.md)와 패키지 README에 있다.

최신 i18n·언어별 Kojo 구조를 유지하며 별도 `game/language-packs/<locale>/entry.js`를 읽는 확장 경로를 제공한다. 신규 `ko-KR` 완역은 이번 범위에 포함하지 않으며 v2.210 한국어판을 병합하지 않았다. 음향의 실제 청취, 원본의 고급 효과와 모든 우선 화면의 직접 플레이는 [UI 현황](ERAUMA_UI_STATUS.md)에 남은 항목으로 기록한다. CrossWorld 공용 ID·세계 시간·게임 간 이동·공유 저장은 이번 단독 호환판의 범위에 포함하지 않는다.
